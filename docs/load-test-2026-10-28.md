# Load test: 50 users, 15 minutes (28 October 2026)

Performance and caching evidence for the A3 report. Supersedes the 22 October run,
which showed no cache activity because it did not hit a cached endpoint.

## Setup

| | |
|---|---|
| Tool | k6 v2.3.0, script `scripts/load.js` |
| Target | `GET https://n12191434.cab432.com/api/campaigns/<id>/dashboard` |
| Campaign | "Always-On Creator Network" (300 creators — the heaviest seeded campaign) |
| Load | 50 virtual users, one request each ~5 s (`sleep(5)`) |
| Duration | 15 min (ran 15m05s) |
| Start | 2026-10-28 13:18:39 AEST (03:18:39 UTC) |
| End | 2026-10-28 13:33:44 AEST (03:33:44 UTC) |
| Account | `load@hookd.test`, Cognito access token via SRP (same flow as the web app) |

The dashboard endpoint is cached per organisation in Redis with a 300 s TTL
(`dashboard_cache_ttl_seconds`) and reports `X-Cache: hit|miss`. Caching was
confirmed before the run: first read `miss`, second read `hit`.

## Results

| Metric | Value |
|---|---|
| Requests | 8,475 (9.36 req/s) |
| **p95 latency** | **292.94 ms** |
| p90 latency | 238.35 ms |
| Median latency | 114.83 ms |
| Mean latency | 320.62 ms |
| Min / Max | 45.19 ms / 60.0 s |
| **Error rate** | **0.18 %** (16 of 8,475) |
| **Cache hit rate** | **99.56 %** (8,422 hits, 37 misses of 8,459 responses) |
| Data received | 1.3 GB (1.4 MB/s) |

Latency breakdown: server wait (`http_req_waiting`) p95 277.82 ms, response transfer
(`http_req_receiving`) p95 29.54 ms. Connection setup was negligible (p95 0 ms) because
connections were reused.

## Notes for the report

- **Caching works and is doing the work.** 99.56 % of reads were served from Redis. With
  a 300 s TTL over 15 min only a few expiries are expected, so the 37 misses are more
  than the ~3 scheduled expiries: when a key expires, several of the 50 concurrent users
  miss at once before the first one repopulates it (a small thundering herd). A
  single-flight lock or early background refresh would cut that further.
- **Payload size, not compute, drives part of the latency.** Each dashboard response is
  about 150 KB, so 50 users pull ~1.4 MB/s. The mean (320 ms) sits well above the median
  (115 ms) because of a few large outliers, not a slow typical request.
- **The 16 errors clustered in one ~30 s window** at 13:23:32 and 13:24:04 AEST, about
  five minutes in. Two were client-side request timeouts; the other 14 were non-200
  responses whose status codes the script did not record (the check only tested
  `status === 200`). One request waited 36.4 s for the server and another spent 25.8 s
  receiving, so the stall was server-side rather than network setup. This is consistent
  with an ECS task recycling or a scale-out event, but that was not confirmed against
  CloudWatch — see below.

## Not verified

The ECS/ALB side of the 13:23–13:24 window was not checked: the AWS SSO session had
expired at the time of the run. To confirm the cause, re-authenticate and compare ECS
task counts and ALB 5xx metrics for 03:23–03:25 UTC on 28 October 2026.

## Reproducing

```sh
export TOKEN=...        # Cognito access token for load@hookd.test
export CAMPAIGN_ID=...  # an active campaign, largest one preferred
k6 run scripts/load.js
```

The token and campaign id are read from the environment so no credential is stored in
the repo. `scripts/load_test.py api` signs in the same way and additionally reports
per-endpoint latency and mixes in uncached reads.
